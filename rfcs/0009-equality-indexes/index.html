Equality and range indexes

Summary

Section titled “Summary”

Moraine adds a native, ordered index over DuckLake table columns. The definition is a catalog entity. Entries live in the index subspace, point at stable row ids, and land in the same commit as the rows they cover. Unique entries are keyed on the value itself, so racing inserts of one value collide in the store. Builds too large for one commit run staged across bounded steps. The planner narrows DuckLake scans through lookups pinned to one read revision.

The index definition

Section titled “The index definition”

An index is an index kind in the current and history keyspaces, keyed (table_id, index_id), with index_id from the global catalog-id counter. The value carries the name, the indexed columns by field id in declared order (so rename_column leaves an index untouched), the unique flag, per-column direction and NULL placement, the maintenance mode, the build state and cursors, the poison flag, and the certificate snapshot. The definition is temporally versioned like every entity; the entries are live-only.

ReadScope and CatalogSnapshot expose indexes_of(table), index_by_name(table, name), index_by_schema_name(schema, name), index_on_columns(table, columns), and index_by_id(table, id). The domain types are IndexId, IndexDef, IndexInfo, IndexState, IndexMaintenance, ColumnOrder, IndexEntry, FileIndexRemoval, and BuildStep. An index name is unique within its schema, compared case-insensitively, checked inside the creating commit.

The Transaction verbs:

Verb Effect
create_index(table, def, backfill) Inserts a ready definition and stages the writer-supplied backfill entries in the same commit. Ascending, NULLS LAST.
create_index_ordered(table, def, orders, backfill) As create_index, with one ColumnOrder per column.
create_index_ordered_with_maintenance(table, def, orders, maintenance, backfill) As create_index_ordered, selecting synchronous or deferred upkeep. Deferred is refused for a unique index.
create_index_staged(table, def) Inserts the definition in building state with no entries.
create_index_staged_ordered(table, def, orders) The staged form with per-column orders.
create_index_staged_ordered_with_maintenance(table, def, orders, maintenance) The staged form with orders and upkeep mode.
build_index_step(index, batch, is_final) Stages one batch of writer-supplied entries, advances the cursor, and flips the index ready when is_final.
record_index_verification(index, observed, at) Records or withdraws the certificate. Refused if the index is not ready or its definition moved since observed.
drop_index(index) Ends the definition into history. Entries are orphaned for later reclamation.

Index DDL is recorded in changes_made as altered_table:<table_id> and sets schema_changed, so it conflicts with concurrent inserts, deletes, and other alters: a create_index racing a register_data_file aborts with CommitConflict and the caller re-drives its backfill against the new file set. The commit protocol defines the conflict matrix.

drop_column, and alter_column with a type change, on a column a live index references fail with Constraint: the encoding is type-bound, so the index must be dropped first. drop_table ends the table’s indexes with it.

create_index refuses columns whose Parquet form and inline Arrow form cannot derive the same bytes: HUGEINT, UHUGEINT, INT128, and UINT128, which DuckDB writes to Parquet as a lossy double, and VARIANT, which has no single scalar to encode. The check is ensure_indexable in crates/moraine/src/catalog/index_policy.rs.

Entry keys

Section titled “Entry keys”

Entries occupy their own subspace, one leading discriminant byte in the Key enum, so entry churn compacts apart from the metadata subspaces. The layout is pinned by golden vectors like every other key kind.

Kind Key components Value
index/unique index_id, canon(values) row_id
index/multi index_id, canon(values), row_id empty

A unique entry’s key is the value alone, so two commits inserting the same value write the same key and collide in SlateDB’s write-write conflict detection; the loser retries, sees the winner’s entry, and returns Constraint. A non-unique entry appends the row id, so rows sharing a value occupy distinct keys and concurrent appends stay benign; a lookup for v is the ascending prefix scan over index/multi/{index_id}/{canon(v)}/. index_id leads both kinds, so each index is one contiguous range that lookups scan and reclamation deletes.

Canonical encoding

Section titled “Canonical encoding”

Entry keys embed column values in a canonical, order-preserving encoding per DuckLake column type: encode(x) < encode(y) as unsigned bytes if and only if x < y in the type’s SQL order. Golden vectors and proptest roundtrips pin it.

Type class Encoding
Integers Fixed-width big-endian with the sign bit flipped, width normalized per column type.
Strings and blobs The UTF-8 or raw bytes, storekey-escaped so component boundaries stay unambiguous. Order is DuckDB’s default binary order.
Floats -0.0 normalized to +0.0, every NaN collapsed to one pattern, then the total-order transform. NaN sorts greatest.
Temporal types Their underlying integer count.
UUID A 16-byte blob on both write paths.
Composite keys Component encodings concatenated in declared column order under storekey tuple framing, so ("ab","c") and ("a","bc") stay distinct and a shorter value sorts before its extension.

A Descending column stores the bitwise complement of its fully framed component, terminator included, so variable-length values reverse correctly; the leading NULL flag is not complemented. NULL placement is per column, NullOrder::First or NullOrder::Last, carried by a leading flag byte on each component. A row with a NULL in any indexed column is stored, so IS NULL can find it; such a row is always multi-shaped and exempt from the value collision, so a unique index admits any number of NULL rows, and an equality lookup on NULL has no answer. Orders are recorded only where they diverge from ascending, NULLS LAST, so an all-default index is byte-identical to one created without orders.

A composite key whose component encodings exceed MAX_INDEX_KEY_BYTES, 1024 bytes, is refused with Constraint at insert or registration.

Coverage

Section titled “Coverage”

Writes to a table with a maintained index must supply or derive entries for every added row and remove entries for every deleted row:

Moment Embedding API Extension path
inline_insert Moraine derives entries from the rows and stages them in the same batch. Same, from the Arrow body DuckLake stages.
Inline flush Nothing. Entries name row ids, which flush preserves. Same.
register_data_file Writer-supplied (ordinal, values) pairs, mapped to row_id_start + ordinal at commit. Moraine reads the registered file’s indexed columns and derives entries.
inline_delete of a store-resident row Moraine recomputes the values from the chunk and stages the removal. Same.
register_delete_file, or inline_delete against flushed rows Writer-supplied FileIndexRemoval values (row_id, values) per killed row. Moraine reads the killed positions from the target file.

On the embedding API, register_data_file, register_delete_file, and inline_delete on an indexed table fail with Constraint when they omit the required entries; a removal must name the row being removed, and a dense target’s row id must lie inside the target’s range.

On the extension path every entry is moraine’s own work: it projects the indexed columns, row positions, and row-id column from a registered file, and reads the killed positions’ values from a delete file’s target. The inline body is encoded losslessly, matching how DuckDB writes Parquet, so a value inserted inline and the same value written to a file derive the same bytes. A commit registering a data or delete file on a table with a maintained index fails with Constraint, naming the file, when moraine has no DATA_PATH store: the lake records no data path, or is encrypted, since moraine reads no byte of an encrypted file. The bundled DuckLake records the attach’s DATA_PATH in the data_path metadata option when the catalog serves none, and moraine adopts it on first use when the attach named no META_DATA_PATH; it is served back as DuckLake’s ducklake_metadata row, and a re-attach supplying a conflicting value is refused. A table whose rows stay inlined needs no data store. A unique index’s scoped read is synchronous at commit and a failed read aborts it; the check is never skipped.

Backfill at creation

Section titled “Backfill at creation”

Inlined rows are backfilled by scanning the chunks; rows in external files need writer-supplied entries, or, for CREATE INDEX, a scoped read of every live data file, so the cost is the table’s indexed columns. The build is one commit and one atomic batch, with uniqueness validated over the assembled set before staging. A backfill above the commit bound returns an error before staging anything, and the caller re-drives it as a staged build. A table that already holds files cannot be indexed without a data store to backfill from.

Re-derivation and compaction

Section titled “Re-derivation and compaction”

A registered file is not always new rows. Multi entries re-derive as idempotent puts and a unique entry already naming the same row is a no-op, so UPDATE rewrites and inline flush do not abort against their own entries. No register-side path stages an entry delete.

A commit whose change set names only compaction derives nothing: ChangeSet::compaction_only_tables returns the tables named by merge_adjacent, rewrite_delete, or the legacy compacted_table kind when nothing else appears, and an inline flush classifies the same way when its only deletes are the flushed tables’ tombstone moves and it deletes no data file. Such a commit’s files are read only for the row-id columns that hold entries to their sources. This keeps a large indexed table compactable, because a merge decides its own batch size and cannot split.

Uniqueness enforcement

Section titled “Uniqueness enforcement”

At commit, each new unique entry is point-read through the transaction: present with a different row id is Constraint, present with the same row id is a no-op, absent stages the put. Duplicates within one commit collide in memory, and the window between the read and a concurrent identical put is closed by the key collision. Entries are live-only, and deletes remove entries in the batch that kills the row, so delete-then-reinsert behaves as SQL expects.

A writer-supplied deletion of a unique entry is dropped unless the stored row id is the row being removed. A deletion the committer derived itself against a ready index skips that read; against a building or poisoned index the guard stays.

The rejection names the index, the claiming row, the holding row, and whether the collision was within the commit or against a stored entry, and carries no key data. Its text avoids the substrings DuckLake’s commit loop retries on, so a rejected bulk INSERT surfaces at once; the extension surface states that wire contract.

Commit bounds

Section titled “Commit bounds”

stage_index_entries refuses a commit above MAX_INDEX_ENTRIES_PER_COMMIT, one million entries, before doing any work, naming the count, the limit, and the remedy of splitting the load. MAX_INDEX_STAGED_BYTES_PER_COMMIT, 64 MiB over encoded key and value bytes, is checked before each write enters the batch. Both are fixed invariants in crates/moraine/src/transaction/index_maintenance.rs, not CatalogOptions.

A staged build step carries two further bounds in BuildStep, settable per call: entries, default one million, bounds one step’s buffer; bytes, default 8 MiB measured on the physical keys staged, bounds the single object-store request a batch becomes, because a batch too large for the request timeout retries forever. A step ends at whichever bound it reaches first and always carries at least one entry.

Row-id payload and lookups

Section titled “Row-id payload and lookups”

The entry payload is a row id. Flush, compaction, and UPDATE rewrites re-home rows and preserve their ids, so no maintenance operation rewrites an entry, and a file’s rows never leave the catalog without a row-grain deletion having taken their entries or a replacement carrying them under preserved ids.

Lookups are accessors on ReadOnlyCatalog in crates/moraine/src/catalog/handle/index_lookup.rs:

Accessor Result
index_lookup(table, index, values) Row ids for one complete equality key. A point get on a unique index, a prefix scan on a non-unique one.
index_lookup_many(table, index, keys) The union of row ids for a set of complete keys, deduplicated and resolved under one head view. An empty set returns no rows after validating the index.
index_range(table, index, lower, upper, reverse) Row ids for a value window. Each bound is Included, Excluded, or Unbounded. Results come back in stored order, or its opposite when reverse is set.
index_nulls(table, index, prefix, reverse) Row ids for an IS NULL query. prefix is a leading run of Some(value) and None, at least one None required.
index_predicate_rows(scope, table, predicates) Selects a ready index for conjunctive predicates. Described under planning.

A range names an equality prefix over the leading columns plus one range on the next column; a bare range on a non-leading column is refused. Comparison predicates never match NULL, so index_range clamps open sides to the non-null region and index_nulls serves the NULL subrange. A multi-column bound is a tuple, and a tuple window requires every named column to sort the same way.

Lookups are head-only: a lookup through read_scope_at(snapshot) returns an error and time travel remains a scan. A lookup against a Building or Maintaining index fails with Error::IndexBuilding. A warm read-write handle serves lookups from the view it already holds; a read-only handle probes under a read session, per the read path.

locate_row_ids(store, prefix, table, row_ids) resolves row ids to FileRowCandidate { row_id, data_file_id } at head, None for a live inlined row or a row located nowhere. Location is derived cache state and adds no index keys.

Staged builds

Section titled “Staged builds”

A backfill larger than one commit runs as a building to ready lifecycle:

  1. The definition commits in building state as altered_table with schema_changed. From this commit forward every writer maintains the index under full coverage, and unique entries are value-keyed.
  2. A derivation pass reads the definition, inline rows, file registrations, schemas, and delete bookkeeping through one snapshot-isolated read session, walks live inline chunks then external files in durable source order, applies deletes as each source is read, and streams entries into steps.
  3. Each step commits as inserted_into_table:<table_id> and advances a source cursor on the definition: an inline cursor of (schema_version, begin_snapshot, chunk_seq) and row offset, and an external cursor of (data_file_id, position). The step checks the derivation snapshot inside its commit closure; a concurrent delete writes deleted_from_table, which conflicts, and the driver re-derives at a fresh snapshot from the durable cursor. An intermediate step mints a snapshot but writes no ducklake_schema_versions row.
  4. When the cursor reaches the end of the live set and the definition is not poisoned, one final commit flips building to ready as altered_table with schema_changed. In-flight writers conflict, re-run, and see ready. From the flip the entry range is byte-identical to a from-scratch build over the same live rows.

The builder covers the rows live at its derivation snapshot; everything committed after the definition is covered by the writer that committed it. A row that dies before its step lands is excluded by the delete bookkeeping, caught by the in-closure snapshot check, or surfaces as CommitConflict, and every case resolves into derivation from a fresh snapshot.

A duplicate found during building poisons the build: whoever finds it stages a terminal poisoned flag on the definition, drops the colliding claim, and lands normally. The driver stops at its next step, ends the definition into history, and surfaces Constraint to the creating caller. Poisoning writes the definition key, so it conflicts with cursor advances and every interleaving converges. Before its first pass a build fills a bloom filter with every unique key the index already holds, so a never-seen key is staged as absent without a read.

The Catalog drivers, create_index_staged(table, def, orders, data_store, data_prefix, step) and create_index_staged_with_maintenance, return once the index is ready or the build has failed; a failed build drops its definition, an interrupted call leaves it building, and calling again with the same def resumes from the cursor. drop_index abandons a build. A data store is required whenever the table has live registered files, checked before creating or adopting a definition, inside the definition’s commit closure, and at the start of every pass; a missing store leaves a resumable build intact. moraine_indexes exposes is_building and state; a poisoned definition reports is_building true, so a caller gating writes on readiness reads state.

Deferred upkeep

Section titled “Deferred upkeep”

An index created with IndexMaintenance::Deferred, refused for a unique index, moves SQL additions out of the data commit: a commit adding covered rows flips the index from ready to maintaining in the same snapshot, persists the repair cursor, and stages no additions. Deletions stay synchronous in every state, so an UPDATE removes the old value in its data commit and leaves the new value for the repair. maintaining serves no lookups. Once the data snapshot is durable, Catalog::repair_deferred_indexes(data_store, data_prefix, step) drives the bounded backfill and flips the index back to ready; intermediate steps classify inserted_into_table and the final flip is FinishIndexMaintenance, an altered_table operation that does not advance schema history. A failed repair leaves the durable maintaining marker, and the maintenance scheduler repairs maintaining indexes before sweeping dropped ones.

Row-id resolution for data files

Section titled “Row-id resolution for data files”

UPDATE, rewrite_data_files, and non-adjacent merge_adjacent_files write a trailing _ducklake_internal_row_id column tagged with DuckDB’s reserved field id ROW_ID_FIELD_ID and record row_id_start as NULL or as the file’s minimum embedded id; a flushed inline file carries both, and its ids may hold gaps. RowIdSource::Resolve takes the embedded column when present, else row_id_start + position, else Corruption; a NULL or negative embedded id is Corruption. RowIdSource::Ordinal serves the extension’s registration helper, whose positions are re-mapped onto a freshly allocated dense range, and refuses a file carrying the embedded column, since registering it under new ids would fork its identity.

Deleted positions are passed to the target’s scoped read, and an entry is removed when its ordinal is named by a delete file or an inline file-delete. Indexed columns are located by field id through the column mapping rules; missing fields use initial_default, and old physical values convert to the current type with checked casts.

Every ducklake_file_column_stats insert, the reserved row-id column’s included, requires a ducklake_snapshot insert in the same commit. A head-preserving maintenance batch may carry only raw deletes, deletion-schedule inserts, ducklake_metadata writes, and inline operations; translate_maintenance in crates/moraine/src/transaction/staged.rs refuses anything else with Constraint.

Extension surface

Section titled “Extension surface”

DuckLake rejects index DDL, so the shim registers an OperatorExtension that binds CREATE INDEX, CREATE UNIQUE INDEX, and DROP INDEX for moraine-backed lakes, and a PlannerExtension for DROP INDEX IF EXISTS, both executing through the core build and drop engine.

CREATE UNIQUE INDEX by_id ON lake.main.users(id);
CREATE INDEX IF NOT EXISTS by_region ON lake.main.users(region)
    WITH (staged = true, step_entries = 100000);
DROP INDEX IF EXISTS lake.main.by_region;

Native DDL requires autocommit and a writable lake, commits autonomously, and returns no rows. Options are staged, step_entries, step_bytes, maintenance, directions, and nulls; step_entries and step_bytes must be positive, and maintenance = 'deferred' is limited to non-unique indexes. DuckDB’s parser discards per-column ASC, DESC, and NULL-placement clauses, so ordering is WITH (directions = ['desc', 'asc'], nulls = ['first', 'last']), one element per column. Expression indexes, partial indexes, PRIMARY KEY, and table-level UNIQUE are unsupported. IF NOT EXISTS tests the schema-level name, and repeating an interrupted staged create without it resumes the build.

The table functions take catalog, schema, table, index as leading strings, written … below; moraine_indexes stops at the table.

Function Effect
moraine_index_lookup(…, v…) (row_id, data_file_id) for one equality key, one variadic value per indexed column.
moraine_index_in(…, keys) Rows for the union of complete keys: a list of scalars for a single-column index, a list of row(...) values for a composite one. A key containing NULL matches no row.
moraine_index_range(…, lower, upper, lower_inclusive, upper_inclusive, reverse := b) Rows for a value window. A NULL bound is an open side.
moraine_index_nulls(…, prefix…, reverse := b) Rows for an IS NULL query. A NULL argument means IS NULL, any other means equality.
moraine_index_verify(…) Recomputes the entry set and reports stored, expected, missing, dead, mismatched, and certified_at.
moraine_indexes(catalog, schema, table) index_id, index_name, is_unique, is_building, state, and certified_at. state is ready, building, maintaining, or poisoned.

Each function resolves the store handle from the attached catalog and the table id from ducklake_table, then drives the same core accessors as the embedding API; the read functions bind their arguments as constants and resolve against the revision the current DuckDB transaction pinned. A Constraint raised on the SQL write path carries none of the substrings DuckLake’s commit loop retries on (conflict, concurrent, unique, primary key), while a genuine CommitConflict does, so DuckLake retries, the re-read finds the winner’s entry, and the permanent Constraint surfaces then. data_file_id is NULL for an inlined or unlocated row, so a statement naming exact rows joins with rowid = row_id AND data_file_id IS NOT DISTINCT FROM hits.data_file_id; tuple IN against these columns drops every NULL file id and is unsafe as a DELETE or UPDATE predicate.

Verification and the certificate

Section titled “Verification and the certificate”

ReadOnlyCatalog::verify_index(table, index, data_store, data_prefix) recomputes the entry set at the current snapshot through the scoped reads the backfill uses and diffs it against the index. IndexVerification reports:

Count Meaning
stored Entries the index holds.
expected Entries the live rows require.
missing A required entry the index does not hold.
dead A held entry no live row requires.
mismatched A unique entry under the right value naming another row.

Verification reads the indexed columns of every live row and holds the stored entry set in memory. A building index is refused.

certify_index runs the pass through a read-write attach and records the outcome with record_index_verification: a clean pass writes the snapshot it agreed at as verified_at_snapshot, a pass that found any discrepancy clears an earlier agreement, and the recording is refused if the definition moved since the pass observed it. A staged build step, a rebuild, and a deferred repair withdraw the certificate; ordinary maintained writes do not. The certificate is a separate field whose only state coupling is requiring Ready; moraine_indexes reports it as certified_at, and a read-only attach reports without writing.

Index-accelerated planning

Section titled “Index-accelerated planning”

DuckLake owns the planner. The extension’s optimizer rule translates pushed constant predicates into conjunctive column comparisons and offers them to ReadOnlyCatalog::index_predicate_rows(scope, table, predicates), which takes IndexPredicate { column, comparison } with IndexComparison an equality list, IsNull, or an inclusive or exclusive bound. It selects a ready index with the longest usable prefix, probes it, and returns IndexPredicateRows { rows, certified_exact }, or None when no ready index covers a leading predicate. The original predicate is still evaluated over the candidate rows. A certified full-key probe with no residual predicate is the one case where a DELETE is rewritten to positional deletion without a scan.

Index scans use four components:

  • IndexReadScope pins catalog, index, file, and inline reads to one committed revision, including DuckLake’s file-list and metadata reads for the statement. IndexReadIdentity lets a plan check whether it can reuse results without retaining the transaction.
  • locate_row_positions_at(scope, data_store, data_prefix, table, pairs) maps (row_id, data_file_id) pairs to LocatedDeletion positions at that revision.
  • LocatedRowScan, returned by scan_rows_at and exposed in SQL as moraine_summary_scan, reads the requested columns at those positions, one Arrow batch at a time.
  • Per-table file directories and row summaries map row ids to files and inline chunks. They update as the file map changes and use the published row summaries.

Candidate row ids and file ids feed DuckLake’s scan as filters on rowid and the virtual data_file_id column, so both the file list and the rows read narrow. Results are memoized per pinned revision. A transaction with staged writes keeps probing at the revision it started on, because entries carry no transaction-local overlay.

The rule declines, leaving the ordinary plan, for a scan at a snapshot other than the transaction’s, a transaction with local inserts, no ready index over a leading predicate, a value of a type the index does not cover, or a failed probe, which is logged. The positional DELETE rewrite additionally requires a certified index, every pushed predicate answered in full, every resolved row in a committed file, no deletion vectors on the table, no RETURNING, and nothing but projections between the delete and its scan. UPDATE keeps the ordinary operator and narrows its reads through the pushed filters.

Format gate and reclamation

Section titled “Format gate and reclamation”

The minimum readable format already includes the index subspace, staged build state, and deferred upkeep, so index operations stamp no format of their own and an older writer that would maintain no entries is excluded at open; the storage format owns the version ladder. Read-only attaches over an indexed store are unaffected.

drop_index, and drop_table ending a table’s indexes, orphan the entry range and delete no entries. Catalog::maintain with sweep_orphaned_index_entries discovers dead index ids by seeking through the index subspace and reclaims each range in head-preserving batches; ids are never reused, so an id absent from the live catalog is dead forever. Maintenance specifies the sweep.
