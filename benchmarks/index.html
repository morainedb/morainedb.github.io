Benchmarks

Moraine replaces DuckLake’s metadata catalog. These harnesses measure key catalog speeds: commit, catalog open, and what a statement reads (outside of Parquet).

Unless stated otherwise, measurements are from a release build on an 8-vCPU x86-64 Linux VM against the in-memory object store.

  • A commit is durable once its write-ahead-log object lands. The writer paces flushes at META_FLUSH_INTERVAL_MS (default 100 ms). A writer with no concurrent commits flushes after a tenth of that, so a lone commit costs about 11 ms. Concurrent commits share one flush.
  • Against a real endpoint the PUT round trip is the floor.

Running the harnesses

Section titled “Running the harnesses”
question command needs
moraine against other DuckLake catalogs cargo xtask bench Postgres on PATH or MORAINE_BENCH_POSTGRES, else that backend is skipped
read path on a published scale cargo xtask clickbench run --clickbench <checkout> --machine <type> a ClickBench checkout, 40 GB of disk, passwordless sudo
where a commit’s time goes cargo xtask commit-bench an S3 endpoint in MORAINE_S3_BUCKET
what a cold reader pays cargo xtask reader-bench an S3 endpoint for round-trip counts
located lookups cargo xtask locate-bench nothing
indexed scan strategies cargo xtask filter-bench <extension> <results-directory> a built extension
the core against a real endpoint cargo xtask s3 nothing; it starts a pinned RustFS
the core in isolation cargo test -p moraine --test it --release -- --ignored --nocapture measure_ nothing
the two needing crate-internal seams cargo test -p moraine --lib --release -- --ignored --nocapture measure_ nothing
peak heap of a staged index build cargo test -p moraine --test staged_build_memory --release -- --ignored --nocapture nothing
a commit’s conflict check against retained snapshots cargo test -p moraine-duckdb --test ducklake_load -- --include-ignored --nocapture measure_staged_conflict_check_by_retained_snapshots a built extension, as cargo xtask e2e sets up
the core against AWS S3 the Real S3 benchmark workflow the AWS stack in CONTRIBUTING.md

The core harnesses use the in-memory object store, so their durable cost is flush wait plus compute; a real store adds its PUT round trip.

Where the time goes

Section titled “Where the time goes”

cargo xtask commit-bench splits an S3-backed one-row UPDATE into DuckLake’s metadata SQL, moraine’s commit work, the durable wait, and the object-store requests. Parquet stays local, so every request counted is metadata.

MORAINE_S3_BUCKET=... MORAINE_S3_PREFIX=... AWS_REGION=... \
  cargo xtask commit-bench [--files 16,128] [--commits 7] [--flush-ms 25]

Loopback RustFS, same VM, medians of seven commits:

files commit DuckLake metadata moraine core durable wait requests
16 23.0 ms 13.4 ms 3.3 ms 3.0 ms 1 PUT, 2.7 ms
128 25.0 ms 14.1 ms 3.4 ms 3.0 ms 1 PUT, 2.9 ms
  • DuckLake’s eight metadata statements are about 60% of the commit. The cost does not grow with the file count.
  • Two statements are 69% of that: the per-column file-list query and the snapshot insert.
  • A local-filesystem store is within 0.2 ms of RustFS, and the task records zero GETs per commit. DuckDB spends the time parsing, binding, and optimising about a kilobyte of generated SQL. Preparing the statement saves the parse, because DuckDB re-binds prepared statements that read a catalog.
  • A CPU profile puts Moraine’s own code and its SlateDB reads under 4% of the commit.

flush interval median commit
1 ms 0.6 ms
10 ms 1.7 ms

A lone writer waits a tenth of the interval plus about 0.5 ms of compute. Before the pacing floor existed it waited the whole interval (103 ms at the default on an Apple M2).

Against other DuckLake catalogs

Section titled “Against other DuckLake catalogs”

cargo xtask bench runs identical workloads against moraine, a DuckDB file catalog, and Postgres through the same pinned DuckDB CLI. Data is local Parquet everywhere; only the catalog differs.

cargo xtask bench [--backends moraine,duckdb,postgres] [--workloads <name>,...]
                  [--scale small|medium|large] [--repeat N]
                  [--concurrency 1,2,4,8] [--commits N] [--indexed]
                  [--flush-interval-ms N]

Defaults: all backends, all workloads, small, three repeats. Postgres is provisioned from binaries on PATH or under /opt/homebrew/opt/postgresql@*; MORAINE_BENCH_POSTGRES names an existing server. Output is a table of median (min…max) per phase with a ratio against moraine, also written to target/bench/report.json.

workload measures
bulk_load CREATE TABLE plus one large INSERT
small_commits K single-row inserts; the headline latency number
many_tables T × CREATE TABLE
scan full and filtered scans, time travel, snapshot listing
maintenance merge_adjacent_files, expire_snapshots, cleanup_old_files
deletes_repeated D single-key deletes, one commit each
deletes_bulk the same rows in one statement
deletes_covering a partition-aligned delete that drops the file
deletes_partial the same, one row short of covering
deletes_indexed_* repeated and covering with an equality index
concurrent_processes N writer processes
concurrent_connections N connections over one instance

Each delete workload gets a lake with one table, because delete cost rises with the table count. Compare repeated with bulk (what N commits cost over one) and covering with partial (what dropping the file saves); do not compare across pairs. The indexed twins add one CREATE INDEX; the other backends have no equality index and skip them. ATTACH is a timed phase.

Single writer

Section titled “Single writer”

bulk_load and small_commits at the small scale, loopback Postgres 16, three repeats:

phase moraine duckdb postgres
attach 8 ms 19 ms 113 ms
CREATE TABLE 53 ms 57 ms 75 ms
100,000-row INSERT 41 ms 45 ms 49 ms
20 single-row inserts 254 ms 218 ms 135 ms

Serial commits pay moraine’s flush each, at the 1 ms interval the latency workloads pin; a loopback Postgres commits in about 7 ms and a DuckDB file in about 11 ms.

Concurrent writers

Section titled “Concurrent writers”

--commits single-row inserts are spread over N writers, released together on a barrier. concurrent_connections uses xtask/cpp/concurrent_writers.c, because the CLI holds one connection. 128 commits, three repeats.

Connections over one instance:

writers moraine duckdb postgres
1 1.47 s 1.08 s 665 ms
4 597 ms 1.78 s 953 ms
8 417 ms 1.76 s 1.77 s
16 461 ms 2.85 s 2.94 s

Within one process, moraine is the only catalog that gets faster with writers, and the fastest from four up. Across processes, both embedded catalogs are single-writer: moraine fences the previous writer with a typed error, and the DuckDB file catalog fails on the file lock. Postgres accepts more writers and gets slower.

These runs use local storage and report median, minimum, and maximum latency. They do not run in CI.

Reads

Section titled “Reads”

Cold reader

Section titled “Cold reader”

cargo xtask reader-bench measures what a fresh read-only process pays over thousands of files: attach (split into store open and first materialization), file listing, a pruned query plan, and a warm repeat. Each repeat is a new process; only --cache-dir survives.

MORAINE_S3_BUCKET=... [MORAINE_S3_ENDPOINT=...] \
  cargo xtask reader-bench [--files 2000,20000] [--tables 1] [--deletes 0]
                           [--repeat 5] [--cache-dir <dir>]

--tables spreads the files over that many tables and queries one. --deletes gives that share of files a delete file.

What an attach reads

Section titled “What an attach reads”

Three in-memory sweeps, median read-only attaches.

measure_attach_cost_by_dead_fraction keeps the live catalog fixed and rewrites statistics so only dead versions grow:

churn rounds current bytes L0 SSTs snapshot bytes attach
0 21,657 1 3,139 1.93 ms
40 32,868 5 5,801 3.55 ms
160 32,868 5 11,479 6.03 ms

Attach cost triples while live entities stay constant. The last two rows differ only in snapshot, one record per commit. compact_store removes the dead versions.

measure_attach_cost_under_get_latency adds latency to every GET, so the GET count is the slope:

per-GET latency churned (38 SSTs) merged (14 SSTs)
0 ms 6.5 ms 8.0 ms
10 ms 202.2 ms 212.2 ms
slope (GETs) 19.6 20.4

At 10 ms per GET the attach costs 31× its in-memory time. The merge cut SSTs by 63% and did not reduce GETs, matching the S3 run above. Measured after a reader stopped writing a checkpoint of its own on open; before that the slopes were 22.6 and 23.7, and before the demand-loaded catalog the merge cut GETs from 14.5 to 12.3.

measure_attach_cost_by_index_size grows only the index subspace:

entries index bytes all SSTs manifest open first view
0 0 6 11 KB 1.90 ms 1.85 ms
262,144 9.5 MB 57 3.5 MB 4.66 ms 3.60 ms
1,048,576 37.8 MB 76 22.9 MB 7.84 ms 5.82 ms

The manifest lists every SST and is read whole, so attach grows with SST count (about 85 µs each), never with bytes. A production attach took 833 s to read 12.8 MB because SlateDB’s default scan fetched one 4 KB block per round trip. Reading 4 MiB ahead with eight fetches in flight fixed it.

Materialization and refresh

Section titled “Materialization and refresh”

measure_refresh_versus_rematerialization (library tests): a cache behind head replays the changelog or rescans. Median of 9:

entities gap commits churn / entities rescan replay
503 1 0.01 1.32 ms 0.10 ms
503 32 0.32 1.75 ms 1.28 ms
503 64 0.61 2.08 ms 2.25 ms
8,003 1 0.001 25.4 ms 1.54 ms
8,003 64 0.04 31.3 ms 6.15 ms

Replaying changes becomes slower than rescanning when about 60% of the catalog has changed; Moraine switches to a rescan at 50%. The changelog cap is 4,096 keys so ordinary bulk flushes stay replayable.

measure_changelog_read_cost: in its own subspace the changelog holds a flat 17,344 bytes at any commit count, and snapshot records are back to 2,985 bytes at 64 commits. Inside the snapshot record it had grown them 6.8×.

Warm reads

Section titled “Warm reads”

measure_warm_read_attribution, 2,000 reads per thread over 50 tables, where a read-only transaction pins the writer’s publication instead of listing the manifest:

threads read-write read-only held view, no check
1 12.2 µs 35 µs 0.41 µs
8 29.6 µs 229 µs 4.1 µs
24 87.0 µs 636 µs 11.1 µs

Reads through the writer plateau near 275,000 reads a second. Reads through a read-only handle plateau near 37,000 a second from two threads up. Before that, when every read-only transaction listed the manifest under one lock, it serialized near 8,000 a second at any thread count: 90 µs, 1,056 µs, and 2,926 µs down the same column. Before the demand-loaded catalog the figures were 0.12 µs and 6.4 µs.

measure_reader_round_trips_under_get_latency, 20 tables:

GET latency warm read-only read round trips cold handle round trips
2 ms 0.04 ms 0.0 47.0 ms 23.5
20 ms 0.05 ms 0.0 300.4 ms 15.0

A warm read through a read-only handle issues no GET: a transaction reuses its handle’s pinned publication for READER_POLL_INTERVAL_MS before listing for a newer one. Before that it issued about two, the manifest listing every transaction paid, and a cold handle 28.3 and 18.3. Metadata reads within the interval require no endpoint round trip; checking for a new publication requires a manifest read.

Decoded value ownership

Section titled “Decoded value ownership”

Question: how much synchronous CPU and allocation does decoding one file record cost compared with deep cloning or sharing an existing value?

cargo test -p moraine --lib --release --locked measure_decoding_and_shared_reuse -- --ignored --nocapture --test-threads=1

2026-11-13, commit 30c961a, 8-vCPU x86-64 Linux sandbox, Intel Xeon 2.90 GHz, Rust 1.96.1 release build with the test allocation counter. Each mode runs 100,000 iterations over a 69-byte framed DataFileValue containing one path string. CPU is measured on the calling thread; no store or I/O is involved.

operation CPU per record allocations per record allocated bytes per record
protobuf decode 99 ns 1 50
deep clone 45 ns 1 50
shared ownership clone 11 ns 0 0

This small-record fixture isolates ownership costs. It does not measure a catalog lookup, larger nested records, or the benefit of a decoded-value cache.

Staged conflict check

Section titled “Staged conflict check”

measure_staged_conflict_check_by_retained_snapshots seeds 128, 512, and 2,048 DuckLake commits carrying 4 KiB of commit info each, stages a write, and runs the changes arm of DuckLake’s commit-time conflict check twenty times. GETs are what the twenty runs issued; the per-check time is amortized against a session that runs none, through the DuckDB CLI over a local store:

retained GETs, every snapshot read GETs, from the floor ms per check, before after
128 302 0 12.8 1.6
512 607 0 7.5 1.1
2,048 1,553 0 noise 0.5

The paged scan read and decoded every retained snapshot and DuckDB filtered afterwards. A cursor that opens at the pushed snapshot_id floor reads the snapshots since the transaction began, which the block cache already holds, so the check issues no object-store read at any retained count.

Probe fetch

Section titled “Probe fetch”

measure_probe_cost_by_index_size, 32 probes across the whole index run:

entries index bytes cold GETs cold bytes / probe warm GETs warm ms / probe
8,192 297 KB 34 4,530 0 0.071
1,048,576 37.8 MB 39 61,595 0 0.072

A cold probe into 37.8 MB fetches 62 KB (a part-grained cache would fetch 4 MiB). A warm probe fetches nothing.

Located lookups

Section titled “Located lookups”

Row summaries (a range, Roaring bitmap, or sorted vector per data file) map a row id to the files that hold it.

cargo xtask locate-bench [--files N] [--rows-per-file N] [--update-batches N] reports summary bytes, cold and warm lookup time, and the files a scan reads with and without the located join.

row_lookups, warm, one hit:

lookup 16 sources 128 1,024
file-located 442 µs 2.45 ms 20.2 ms
inline membership 188 µs 194 µs 288 µs
recent_row 91 µs 84 µs 83 µs

Inline and recent lookups are flat. A file-located lookup costs about 20 µs per registered file, because the demand-loaded catalog streams the file inventory a page at a time. A retained directory previously answered in 35 µs at any size. Cold, it also reads one footer per dense file.

Scan strategies

Section titled “Scan strategies”

cargo xtask filter-bench <extension> <results-directory> times wide located filters against clustered, scattered, and broad matches. --baseline <extension> compares a second build; --fixture <directory> reuses an earlier run’s data. Output is CSV.

Staged index build

Section titled “Staged index build”

measure_staged_build_peak_heap profiles one create_index_staged call with dhat’s allocator, 1,024-byte string values, 8 MiB cache:

chunks × rows step entries peak heap retained at return time
16 × 128 128 3.40 MB 2.65 MB 0.36 s
128 × 128 128 22.80 MB 21.08 MB 4.9 s
128 × 128 16 25.16 MB 22.63 MB 74 s
16 × 1,024 128 23.56 MB 21.06 MB 3.5 s

BuildStep.entries bounds the commit buffer, not the heap; most of the peak is the resulting index and store buffers. A smaller step costs 15× the time for no memory gain. Before streaming, the 128 × 128 case peaked at 40 MB.
